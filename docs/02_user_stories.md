# УП2. Пользовательские истории и критерии приёмки

Формат истории: «Как *роль*, я хочу *действие*, чтобы *ценность*».
Формат критерия: **Given** (дано) — **When** (когда) — **Then** (тогда). Каждый критерий проверяется автоматическим тестом или одним HTTP‑запросом: в нём указан маршрут, код ответа и наблюдаемый результат.

Обозначения: `S` — student, `O` — operator, `A` — admin. Ошибки возвращаются в едином формате `{"error": {"code", "message", "details"}}` (см. `05_api_contract.md`).

## US‑01. Регистрация
Как **гость**, я хочу зарегистрироваться по email и паролю, чтобы получить доступ к подаче заявок.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑01.1 | в БД нет пользователя `user1@college.edu` | отправлен `POST /auth/register` с `email=user1@college.edu`, `full_name="Иван Петров"`, `password="Secret123!"` | ответ **201**; в теле `role="student"`, `is_active=true`, есть `id`; поля `password` и `password_hash` в теле отсутствуют |
| AC‑01.2 | пользователь `user1@college.edu` уже зарегистрирован | повторно отправлен `POST /auth/register` с тем же email | ответ **409**, `error.code="conflict"`; количество пользователей в БД не изменилось |
| AC‑01.3 | регистрация AC‑01.1 выполнена | прочитана строка пользователя в таблице `users` | значение `password_hash` не равно `"Secret123!"`, начинается с `scrypt$`, а `verify_password("Secret123!", hash)` возвращает `True` |

## US‑02. Вход
Как **зарегистрированный пользователь**, я хочу войти по email и паролю, чтобы получить токен доступа.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑02.1 | активный пользователь `user1@college.edu` с паролем `Secret123!` | `POST /auth/login` с верной парой | ответ **200**; в теле `access_token` (строка) и `token_type="bearer"`; в декодированном токене есть `sub` (= id), `role` и `exp` позже текущего времени |
| AC‑02.2 | тот же пользователь | `POST /auth/login` с паролем `Wrong123!` | ответ **401**, `error.code="unauthorized"`, токена в теле нет |
| AC‑02.3 | пользователь существует, но `is_active=false` | `POST /auth/login` с верным паролем | ответ **403**, `error.code="user_inactive"`, токен не выдан |

## US‑03. Профиль
Как **авторизованный пользователь**, я хочу видеть свой профиль, чтобы проверить свои данные и роль.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑03.1 | запрос без заголовка `Authorization` | `GET /users/me` | ответ **401**, заголовок `WWW-Authenticate: Bearer` |
| AC‑03.2 | валидный токен пользователя `user1@college.edu` | `GET /users/me` с `Authorization: Bearer <token>` | ответ **200**; `email="user1@college.edu"`, `role="student"`; поля `password_hash` в теле нет |

## US‑04. Категории
Как **администратор**, я хочу создавать, переименовывать и удалять категории, чтобы студенты выбирали тему заявки из актуального списка.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑04.1 | токен admin, категории «Библиотека» нет | `POST /categories` с `name="Библиотека"` | ответ **201**; `GET /categories` содержит «Библиотека» |
| AC‑04.2 | токен student | `POST /categories` с `name="Спорт"` | ответ **403**, `error.code="forbidden"`; категория не создана |
| AC‑04.3 | токен admin, категория «IT» существует | `POST /categories` с `name="IT"` | ответ **409**, `error.code="conflict"` |

## US‑05. Создание заявки
Как **студент**, я хочу создать заявку с темой, описанием, приоритетом и категорией, чтобы сообщить о проблеме.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑05.1 | токен student, категория `id=1` существует | `POST /tickets` с `title="Не работает Wi‑Fi"`, `description="В ауд. 214"`, `priority=3`, `category_id=1` | ответ **201**; `status="new"`, `author_id` = id студента, `assignee_id=null`; в аудите заявки одна запись `action="ticket_created"` |
| AC‑05.2 | токен operator | `POST /tickets` с корректным телом | ответ **403**; число заявок в БД не изменилось |
| AC‑05.3 | токен student | `POST /tickets` с `title="ab"` (2 символа) или `priority=6` | ответ **422**, `error.code="validation_error"`, в `details` указано поле `title` / `priority` |

## US‑06. Список заявок с фильтрацией
Как **пользователь**, я хочу видеть список заявок с фильтрами, чтобы находить нужные мне.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑06.1 | студент A создал 2 заявки, студент B — 1 заявку | A выполняет `GET /tickets` | ответ **200**, в списке ровно 2 заявки, у всех `author_id` = id студента A |
| AC‑06.2 | admin, в БД 3 заявки: 2 в статусе `new`, 1 в `in_progress` | `GET /tickets?status=new` | ответ **200**, ровно 2 заявки, все со `status="new"` |
| AC‑06.3 | любой авторизованный пользователь | `GET /tickets?status=unknown` | ответ **422**, `error.code="validation_error"` |

## US‑07. Просмотр заявки
Как **пользователь**, я хочу открыть заявку по id, чтобы увидеть её детали.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑07.1 | заявка `id=1` создана студентом A | студент B выполняет `GET /tickets/1` | ответ **403**, `error.code="forbidden"` |
| AC‑07.2 | токен admin | `GET /tickets/9999` (заявки нет) | ответ **404**, `error.code="not_found"` |

## US‑08. Назначение исполнителя
Как **администратор**, я хочу назначить оператора на заявку, чтобы за неё отвечал конкретный человек.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑08.1 | заявка `id=1` без исполнителя, пользователь `id=5` — активный operator | admin: `PATCH /tickets/1/assign` с `assignee_id=5` | ответ **200**, `assignee_id=5`; в аудите запись `action="assigned"` с `actor_id` = id админа |
| AC‑08.2 | пользователь `id=2` имеет роль student | admin: `PATCH /tickets/1/assign` с `assignee_id=2` | ответ **422**, `error.code="invalid_assignee"`; `assignee_id` заявки не изменился |
| AC‑08.3 | токен student | `PATCH /tickets/1/assign` | ответ **403** |

## US‑09. Смена статуса
Как **оператор**, я хочу переводить заявку по статусам `new → in_progress → resolved → closed`, чтобы отражать ход работы.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑09.1 | заявка `new`, назначена на оператора O | O: `PATCH /tickets/1/status` с `status="in_progress"` | ответ **200**, `status="in_progress"`, `updated_at` больше `created_at`; в аудите `action="status_changed"` |
| AC‑09.2 | заявка в статусе `new` | O: `PATCH /tickets/1/status` с `status="closed"` (пропуск шагов) | ответ **409**, `error.code="invalid_transition"`; статус остался `new` |
| AC‑09.3 | заявка назначена на оператора O1 | оператор O2 меняет статус | ответ **403**; статус не изменился |

## US‑10. Комментарии
Как **участник заявки** (автор, исполнитель, admin), я хочу оставлять комментарии, чтобы обсуждать решение.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑10.1 | студент — автор заявки `id=1` | `POST /tickets/1/comments` с `text="Проблема повторилась"` | ответ **201**; `GET /tickets/1/comments` возвращает этот комментарий с `author_id` студента; в аудите `action="commented"` |
| AC‑10.2 | студент, который **не** является автором заявки `id=1` | `POST /tickets/1/comments` | ответ **403**; число комментариев не изменилось |

## US‑11. Аудит
Как **оператор или администратор**, я хочу видеть журнал действий по заявке, чтобы понимать, кто и когда её менял.

| ID | Given | When | Then |
|----|-------|------|------|
| AC‑11.1 | заявка создана, назначена и переведена в `in_progress` | admin: `GET /tickets/1/audit` | ответ **200**; 3 записи в хронологическом порядке: `ticket_created`, `assigned`, `status_changed` |
| AC‑11.2 | токен student | `GET /tickets/1/audit` | ответ **403** |

| ID | Given | When | Then |

| AC‑12.2 | токен operator | `GET /reports/summary` | ответ **403** |
